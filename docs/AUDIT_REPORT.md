# Отчёт о security-аудите сервиса «АвтоДай.рф»

Дата: 30.08.2026. Объект аудита: текущая кодовая база АвтоДай.рф (Node.js/
TypeScript/Express backend + Telegram/MAX-боты + SPA-фронтенд).

## 1. Методология

Полный проход по кодовой базе с фокусом на: (1) аутентификацию и авторизацию,
(2) обработку и хранение файлов, (3) сетевые границы (rate limiting, CORS,
CSRF, заголовки), (4) валидацию входных данных, (5) обработку ошибок и
устойчивость процесса, (6) конфигурацию окружения и секреты, (7) специфику
интеграции с внешними платформами (Telegram, MAX).

## 2. Реализованные и проверенные защитные механизмы

- **Проверка подлинности Telegram WebApp `initData` и MAX `initData`**
  (`src/utils/telegramAuth.ts`, `src/utils/maxAuth.ts`) — HMAC-SHA256 по
  официальному алгоритму обеих платформ, сравнение хэшей через
  `crypto.timingSafeEqual` (защита от timing-атак), проверка `auth_date` с
  окном в прошлое (24 часа) и в будущее (5 минут — защита от рассинхронизации
  часов клиента). Поддельный `user_id` без знания токена бота невозможен.
- **Валидация загружаемых изображений в два независимых слоя**
  (`src/server/middleware/upload.ts`): проверка магических байт файла
  (`isValidImageFile`) — не доверяем `Content-Type`, который присылает
  клиент; и защита от «image bomb» через `sharp` с `limitInputPixels` и
  ограничением стороны изображения (5000px) до декодирования полного
  пиксельного буфера.
- **Сжатие фото «на лету» в WebP с бюджетом размера** — каждое загруженное
  фото (объявления автомобилей, рассылка из админки) принудительно
  перекодируется в WebP с итеративным снижением качества/разрешения до
  ~150 КБ (жёсткий потолок 200 КБ). Побочный эффект: перекодировка стирает
  весь EXIF (включая геометки съёмки) и любой полиглот-контент, спрятанный
  после валидных данных изображения.
- **Rate limiting в три эшелона**: общий IP-лимит на всё приложение, более
  строгий на `/api` (better-sqlite3 синхронный — блокирует event loop на
  время запроса), и по-пользовательский лимит на дорогие write-эндпоинты
  (бронирование, публикация объявления, загрузка фото, рассылка) — считается
  по `telegram_id`, а не по IP, чтобы не наказывать всех пользователей одного
  NAT/мобильного оператора.
- **CSRF-защита для cookie-сессий** (`src/server/middleware/csrf.ts`) —
  независимый от `SameSite=Lax` второй эшелон: сверка заголовков
  `Origin`/`Referer` с каноничным доменом сервиса (`PUBLIC_ORIGIN`) на всех
  мутирующих `/api`-запросах, аутентифицированных cookie. Запросы Mini App с
  подписанным `initData` не проверяются этим слоем — там ambient-cookie не
  используется вообще, подделать подписанный initData нельзя.
- **Helmet с точечными, объяснёнными исключениями**, а не отключением CSP
  целиком: `frame-ancestors` снят (иначе Telegram/MAX не смогут встроить
  Mini App в свой WebView), `script-src` разрешает только `'self'` + домены
  официальных SDK Telegram/MAX + Tailwind CDN (только для промо-страниц),
  `referrer-policy` ослаблен точечно для совместимости с Telegram Login
  Widget.
- **Cookie веб-сессии**: `httpOnly` + `Secure` + `SameSite=Lax`, токен —
  `crypto.randomBytes(32)` (256 бит энтропии), хранится на сервере как
  непрозрачный идентификатор (не JWT — подделать содержимое нечем, так как
  содержимого нет). Код входа для браузерной версии сверяется через
  `crypto.timingSafeEqual`.
- **`db.transaction()`** вокруг многошаговых операций с БД (бронирование,
  отмена) — атомарность при использовании синхронного `better-sqlite3`.
- **Whitelist-валидация всех enum-полей на сервере** (`car_class`,
  `transmission`, `fuel_type`, `city`) независимо от того, что прислал
  клиент — `city` дополнительно ограничен курируемым каталогом городов РФ
  (`src/db/cities.ts`), а не произвольной строкой; спецсимволы в поиске по
  `brand` экранируются перед подстановкой в SQL `LIKE`.
- **`CHECK`-ограничения в самой схеме БД** (`src/db/schema.sql`) на все
  enum- и диапазонные поля — вторая линия защиты на случай, если валидация
  на уровне приложения где-то будет обойдена или изменена по ошибке в
  будущем релизе.
- **Глобальный перехват необработанных ошибок** —
  `process.on('unhandledRejection'/'uncaughtException')` в `src/index.ts` —
  плюс `try/catch` вокруг каждой периодической задачи и вокруг остановки
  ботов по сигналу (`SIGINT`/`SIGTERM`), чтобы один сбой в фоне не ронял
  сразу весь процесс (бот + API + сайт).
- **Изоляция доступа к договору аренды** — `GET /api/legal/contract/:id`
  проверяет, что запрашивающий является одной из двух сторон именно этой
  брони, и что бронь имеет статус `confirmed`/`completed`, прежде чем отдать
  документ с именами, телефонами и суммой сделки.
- **Сознательный отказ от сбора избыточных персональных данных** — сервис не
  запрашивает паспортные данные, ВУ, VIN, СТС через приложение (это поля
  информационного посредника по ст. 1253.1 ГК РФ, не хранилища документов);
  договор аренды генерируется с этими полями пустыми для заполнения от руки.

## 3. Найденные проблемы и статус исправления

| # | Категория | Проблема | Статус |
|---|---|---|---|
| 1 | Config / secrets hygiene | В `.env.example` был объявлен `SESSION_SECRET`, который нигде не читается кодом (веб-сессии используют случайные `crypto.randomBytes` токены, не подписанные JWT — секрет для подписи им не нужен). Мёртвая переменная в примере конфигурации вводит оператора в заблуждение — он может решить, что это критичный для безопасности секрет, которым на самом деле ничего не защищено. | **Исправлено** — переменная удалена из `.env.example`. |
| 2 | Deployment / TLS | Интеграция с MAX (`business.max.ru`) требует доверия к сертификату **Russian Trusted Root CA** (Минцифры России), которого нет в стандартном доверенном хранилище Node.js. Если основной сервер развёрнут не в российском дата-центре (типичный сценарий на bothost), исходящие HTTPS-запросы к API MAX будут падать с `UNABLE_TO_VERIFY_LEAF_SIGNATURE` без явной диагностики. | **Исправлено** — сертификат `certs/russian_trusted_ca.pem` возвращён в репозиторий, `src/index.ts` логирует текущее значение `NODE_EXTRA_CA_CERTS` при старте и явно предупреждает, если `MAX_BOT_TOKEN` задан, а `NODE_EXTRA_CA_CERTS` — нет. Инструкция — в `README.md` и `.env.example`. |
| 3 | Robustness — множественная загрузка фото | При добавлении нескольких фото объявления за один запрос (`POST /api/cars/:id/photos`, до 10 файлов) нужно было убедиться, что один повреждённый файл в пакете не приводит к отбраковке уже провалидированных соседних. | **Подтверждено корректным** — каждый файл в `carsRouter` валидируется и перекодируется независимо в цикле; сохраняются только прошедшие проверку. |
| 4 | Bug — часовые пояса | Расчёт срока/стоимости аренды не должен зависеть от часового пояса конкретного города (сервис работает по всей России, 11 часовых поясов). | **Подтверждено корректным** — договор аренды и все связанные расчёты оперируют календарными датами (`YYYY-MM-DD`) без времени и часового пояса; `src/utils/dateFormat.ts` форматирует и сравнивает даты вручную через `Date.UTC`, не через `new Date(iso).toLocaleString(...)` с локальным TZ, что исключает сдвиг на день в восточных часовых поясах. |
| 5 | Access control — множественная загрузка | Лимит «не более 10 фото на объявление» должен проверяться на сервере, а не только в UI (клиент можно обойти прямым запросом к API). | **Подтверждено корректным** — `carsRouter` считает уже сохранённые фото через `countListingPhotos` и отклоняет превышение лимита до записи новых файлов. |

## 4. Известные ограничения этой итерации

- Каталог городов — курируемый список крупнейших городов РФ (~170), не
  полный реестр ФИАС/ОКТМО (~2000+ единиц). Расширяется точечно по запросу.
- Договор аренды не хранит сгенерированный документ (генерируется on-the-fly
  из текущих данных брони) — если нужна юридически значимая версия «как было
  подписано», потребуется сохранение снапшота при первой генерации.
- Интеграция с MAX Mini App использует тот же контракт проверки `initData`,
  что и Telegram (HMAC-SHA256, `WebAppData`-секрет), но не тестировалась на
  реальных данных от MAX в проде — при первом реальном трафике стоит сверить
  формат `initData`, который присылает MAX WebView, с реализацией в
  `src/utils/maxAuth.ts`.
- Административная панель функциональна (пользователи, объявления, брони,
  поддержка, рассылка), но не аудировалась так же глубоко, как основные
  пользовательские сценарии поиска/бронирования — стоит вернуться к ней
  отдельным проходом перед масштабным ростом числа админов.

## 5. Рекомендации перед продакшен-запуском

1. Задать `PUBLIC_ORIGIN`, `BOT_TOKEN`, `WEBAPP_URL`, `ADMIN_IDS` в `.env`
   на хостинге (см. `.env.example`).
2. Если подключается MAX — задать `NODE_EXTRA_CA_CERTS=./certs/russian_trusted_ca.pem`
   и проверить логи старта на предупреждение об отсутствующей переменной.
3. Прогнать `npm run typecheck` и ручное smoke-тестирование основных
   сценариев (поиск → бронирование → подтверждение → договор) перед
   деплоем.
4. Зарегистрировать кириллический домен `автодай.рф` в BotFather
   (Bot Settings → Menu Button / Web App) и в настройках MAX-бота.
